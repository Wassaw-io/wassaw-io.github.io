A 99.97% score in testing, and under 0.1% of new attacks caught

A small company wanted a model to flag attacks in its network traffic. A random forest trained on one kind of attack scored 99.97% F1 in cross-validation, and on seven kinds of attack it had not seen, it caught almost nothing. The useful questions turned out to be how many alerts the team could review and how many labelled examples a new attack needs.

ProblemWhether a traffic classifier would catch attacks, including kinds it was not trained on, without burying the team in alerts.

What I didTrained a random forest on labelled denial-of-service traffic with network identifiers removed, tested it on seven other attack types, compared it with an anomaly detector trained only on normal traffic, and turned every threshold into alerts per day.

DecisionJudge a detector on attack types held out from training, set its threshold from the number of alerts the team can review, and label about 100 examples of each attack type that matters. That took a held-out port scan from 0% to 99% caught, at about 85 to 100 alerts a day.

A standard evaluation against this analysis

A standard evaluation

Reports cross-validated accuracy on the same capture the model was trained on (99.97% F1 here), and uses the default threshold of 0.5.

This analysis

Tests on attack types the model never saw (under 0.1% of each caught at the default threshold), shows every threshold as alerts per day, and measures what a few labelled examples add (port scans and FTP password guessing from 0% to 99%).

When the simple evaluation is enough: if the only threat that matters is the one in the training data, the standard model is fine. It caught 99.95% of that attack in cross-validation, with almost no false alarms.

The test that matters

The dataset records which addresses the attacks came from and when, so a model allowed to see addresses, ports, or timestamps can learn the experiment’s schedule instead of what an attack looks like. I removed all of those and kept 78 statistics that describe each flow’s behavior (sizes, timings, flags). The forest was trained on denial-of-service traffic and then scored on seven attack types from other days.

None of the seven new attack types was caught until about 100 examples of each were labelled

Share of attack flows caught at the default threshold: the model trained on denial-of-service only, and the same model with 100 labelled flows of that attack added to training.

Table view

One hundred examples took port scans and FTP password guessing to 99% caught, cross-site scripting to 93%, and SSH password guessing to 84%, while normal traffic raised alerts at about the same rate as before. Botnet traffic was the hardest, at 38%. One caveat: the labelled examples came from the same attack session as the flows they were tested on, so this is closer to catching a repeat of an attack than a variant of it.

The alerts the team can handle

The other way to catch more is to lower the threshold. Every threshold flags some share of normal traffic, and at about 530,000 normal flows in a working day, even 1% is about 5,100 alerts a day. Move the slider to see what each alert budget buys.

Lowering the threshold catches some new attacks, at thousands of alerts a day

Share of each new attack type caught at a given share of normal traffic flagged, for the forest (filled) and the anomaly detector trained on normal traffic only (outlined).

The usual advice for attacks nobody has labelled is an anomaly detector. Here it did better than the forest only on the botnet traffic, and neither caught SSH password guessing at any budget a team could review. For this data, labelling a few examples beat both threshold tuning and the anomaly detector.

What holds generally, and what is specific to this data

Three lessons hold for any detector. Cross-validation inside one data set says little about new kinds of events, so a detector needs a test set made of event types it never saw. A threshold is a decision about alert volume, and it should be stated as alerts per day. And identifiers such as addresses and timestamps have to be removed before training, or the model learns the data set instead of the problem.

The sizes are specific to this data: the 99.97% F1, the recall for each attack type, and the 530,000 flows a day.

Where else this applies

The same evaluation applies to fraud detection, equipment fault detection, spam and content moderation, and quality inspection, anywhere a detector meets new kinds of events after it is deployed.

Details for technical readers

Data. CIC-IDS2017 (Sharafaldin, Lashkari, and Ghorbani, ICISSP 2018), the labelled flow CSVs for Monday (normal only), Tuesday, Thursday morning, and the three Friday captures. Up to 120,000 normal and 60,000 attack flows were sampled per file. Dropped: flow ID, source and destination IP and port, timestamp. The remaining 78 features get a signed log transform, since they span nine orders of magnitude.

Models. Random forest with 120 trees and a minimum of 2 samples per leaf, trained on the Friday afternoon denial-of-service capture. Isolation forest with 200 trees, fitted on half of Monday’s normal traffic, with thresholds set on the other half. For the forest, each alert budget uses the lowest threshold whose actual rate on normal traffic from the test days stays within the budget, because many normal flows score exactly 0.

Labelled examples. For each attack type with at least 600 flows, 100 randomly chosen flows are added to the training set and the rest are the test set. SQL injection had only 21 flows, too few to test this way.
